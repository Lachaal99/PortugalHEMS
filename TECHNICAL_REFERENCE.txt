1. PROJECT OVERVIEW
================================================================================

1.1 OBJECTIVE
   - Develop an intelligent Home Energy Management System (HEMS) using
     Reinforcement Learning (RL) to optimize household energy consumption
   - Optimize battery storage charging/discharging decisions
   - Optimize EV (Electric Vehicle) charging scheduling
   - Minimize electricity costs by leveraging price variations
   - Reduce peak grid load through smart demand management
   - Learn adaptable policies that respond to real-time energy conditions

1.2 KEY CHARACTERISTICS
   - Real-world Portuguese energy data (prices, PV generation, weather, loads)
   - Modular architecture supporting multiple RL algorithms (DQN, SAC, PPO)
   - Continuous action space mapped to discrete controls
   - 15-minute resolution time steps (96 steps per day)
   - GPU support for efficient training
   - Comprehensive logging and visualization
   - State-of-the-art algorithms (Double DQN, Soft Actor-Critic)

2. ENVIRONMENT DESIGN (EnergyEnv)
================================================================================

2.1 ENVIRONMENTAL PARAMETERS

   Temporal Resolution:
   - Time step (dt): 0.25 hours = 15 minutes
   - Episode length: 96 steps (1 full day)
   - Data frequency: 15-minute intervals

   Calendar Information (encoded in state):
   - Season: [0, 4] normalized
   - Day type: [0, 7] (weekday/weekend) normalized
   - Hour of day: [0, 96] normalized

2.2 STATE SPACE

   State Dimension: 9 (vector of normalized values ∈ [0, 1])

   State Components:
   ┌─────────────────────────────────────────────────┐
   │ Index │ Component          │ Range  │ Unit      │
   ├───────┼───────────────────┼────────┼───────────┤
   │ 0     │ Temperature       │ [0,1]  │ Normalized│
   │ 1     │ Load (consumption)│ [0,1]  │ Normalized│
   │ 2     │ Battery SOC       │ [0,1]  │ Relative  │
   │ 3     │ EV SOC            │ [0,1]  │ Relative  │
   │ 4     │ PV Generation     │ [0,1]  │ Normalized│
   │ 5     │ Electricity Price │ [0,1]  │ Normalized│
   │ 6     │ Season            │ [0,1]  │ Normalized│
   │ 7     │ Day Type          │ [0,1]  │ Normalized│
   │ 8     │ Hour of Day       │ [0,1]  │ Normalized│
   └─────────────────────────────────────────────────┘

   Normalization:
   - Temperature: min=-10°C, max=40°C → [0,1]
   - Load: 90th percentile as max
   - PV Generation: 90th percentile as max (Watts)
   - Price: 90th percentile as max (EUR/MWh)
   - SOC values: Direct state of charge (0 = empty, 1 = full)

2.3 ACTION SPACE

   Raw Action Space: Continuous [-1, 1]²
   - Dimension 0: Battery power command (P_bat) [-1, 1]
   - Dimension 1: EV power command (P_ev) [0, 1] (clipped)

   Continuous Mapping:
   - P_bat ∈ [-1, 1]: -1 = full discharge, +1 = full charge
   - P_ev ∈ [-1, 1]: Clipped to [0, 1], only charge when plugged

   DQN Action Discretization:
   - Battery levels: 7 (linspace from -1 to 1)
   - EV levels: 7 (linspace from -1 to 1)
   - Total discrete actions: 7 × 7 = 49 joint actions
   - Stored in ACTION_TABLE for deterministic mapping

   SAC Action Space:
   - Continuous output from actor network
   - Tanh activation maps to [-1, 1]
   - Action sampling: N(μ, σ) → tanh(z) for exploration

2.4 BATTERY COMPONENT

   Specifications:
   - Capacity: 10 kWh
   - Max charge rate: 5 kW
   - Max discharge rate: 5 kW
   - Efficiency: 0.9 (both charge and discharge)
   - Initial SOC: 0.0 (empty)

   Dynamics:
   E(t) = action(t) × max_charge_rate × dt
   SOC(t+1) = clip([0, 1], SOC(t) + (E(t) × η) / E_capacity)

   Reward:
   bat_reward = -max(0, -SOC, SOC - 1.0)
   Penalties for violating SOC constraints

2.5 ELECTRIC VEHICLE COMPONENT

   Specifications:
   - Capacity: 60 kWh (typical EV)
   - Max charge rate: 7 kW
   - Max discharge rate: 7 kW (V2H capable)
   - Efficiency: 0.9
   - Arrival time: 6 PM (hour index 72 of 96)
   - Departure time: 8 AM (hour index 32 of 96)

   Charging Logic:
   - Only charges when plugged in (outside arrival-departure window)
   - Discharge attempts penalized: -5.0
   - Charging when not plugged penalized: -5.0
   - Departure with SOC < 80% penalized: -10.0 × (1 - SOC)

   Constraint Penalties:
   - Violation of SOC bounds: -max(0, -SOC, SOC - 1.0)
   - Strategic penalties encourage full charge before departure

2.6 POWER BALANCE & REWARD CALCULATION

   Power Balance Equation:
   P_grid(t) = max(0, P_bat(t) + P_load(t) + P_ev(t) - P_pv(t))

   Where:
   - P_bat: Battery power (positive = discharge to grid)
   - P_load: Non-flexible household load
   - P_ev: EV charging power
   - P_pv: Solar PV generation
   - P_grid: Power drawn from grid (always ≥ 0)

   Cost Calculation:
   cost(t) = P_grid(t) × price(t) × dt
   - Unit: EUR per timestep
   - dt = 0.25 hours = 15 minutes

   Step Reward:
   reward(t) = -cost(t) + bat_reward(t) + ev_reward(t)

   Daily Episode Objective:
   J = Σ(t=0 to 95) reward(t)
   = -Σ cost(t) + Σ bat_reward + Σ ev_reward

   Optimization Goal:
   - Minimize total grid electricity cost
   - Manage storage constraints
   - Ensure EV departure readiness

4.2 DQN AGENT DETAILS

   Algorithm: Double DQN with Dueling Architecture + Prioritized Experience Replay

   4.2.1 ARCHITECTURE

       Input: State vector (9,)
         │
         ▼
       Shared Trunk:
       - Linear(9, 256) + LayerNorm + LeakyReLU(0.1)
       - Linear(256, 256) + LayerNorm + LeakyReLU(0.1)
         │
         ├──────────────────┬──────────────────┐
         ▼                  ▼                  ▼
       Value Stream      Advantage Stream
       - Linear(256, 128)  - Linear(256, 128)
       + LayerNorm          + LayerNorm
       + LeakyReLU          + LeakyReLU
       - Linear(128, 1)    - Linear(128, 49)
         │                  │
         ▼                  ▼
       Q(s,a) = V(s) + [A(s,a) - mean(A(s,a))]

   Architecture Rationale:
   - Dueling split: Separates state value from action advantage
   - LayerNorm: Stabilizes training despite diverse feature scales
   - LeakyReLU: Avoids dead neurons in negative reward environments
   - Shared trunk: Reduces parameters, improves learning efficiency

   4.2.2 HYPERPARAMETERS

       Discount Factor (γ): 0.99
       Learning Rate (α): 3e-4 (Adam optimizer)
       Batch Size: 256
       Buffer Capacity: 100,000 transitions
       Minimum Buffer Size: 2,000 (warm-up before training)

       Exploration Parameters:
       - ε_start: 1.0 (full exploration)
       - ε_end: 0.05 (5% random action at convergence)
       - ε_decay_steps: 50,000 (linear decay schedule)

       Target Network (Soft Update):
       - Polyak coefficient (τ): 0.005
       - Update rule: θ_target ← τ·θ_online + (1-τ)·θ_target
       - Applied every training step

       Gradient Clipping:
       - Max gradient norm: 10.0 (L2 norm clipping)

   4.2.3 PRIORITIZED EXPERIENCE REPLAY (PER)

       Enable Flag: USE_PER = True

       Sampling Priority:
       - Priority: p_i ∝ |TD_error_i|^α
       - α (priority exponent): 0.6
       - Higher TD-error transitions sampled more frequently

       Importance Sampling Weights:
       - Weight: w_i = (1 / (N × p_i))^β
       - β (IS weight exponent): 0.4 → 1.0 (annealed)
       - Anneal schedule: 100,000 steps
       - Corrects bias from non-uniform sampling

       Update Rule:
       - TD error = |Q_pred - Q_target|
       - Priorities updated after each training step
       - Small constant (ε=1e-6) prevents zero priority

   4.2.4 TRAINING ALGORITHM

       Input: Environment, number of episodes
       Output: Trained online network

       For each episode:
       1. Reset environment, get initial state s_0
       2. For each step t = 0 to 95:
          a) Select action: a_t ~ ε-greedy(Q_online)
          b) Execute action: (s', r, done, info) = env.step(a_t)
          c) Store transition: buffer.push(s, a, r, s', done)
          d) Update total_steps counter
          e) Every TRAIN_FREQ steps:
             - Sample batch from buffer (using PER)
             - Compute Q-targets using Double DQN
             - Minimize Huber loss (weighted by IS weights)
             - Soft-update target network (Polyak)
             - Update transition priorities (TD-error)

       Training Hyperparameters:
       - TRAIN_FREQ: 4 (update every 4 environment steps)
       - LOG_INTERVAL: 10 (log every 10 episodes)
       - SAVE_INTERVAL: 100 (save checkpoint every 100 episodes)

   4.2.5 DOUBLE DQN UPDATE

       Standard DQN Problem: Overestimation of Q-values
       Solution: Decouple action selection and evaluation

       Double DQN Update:
       - Online network selects best next action: a* = argmax_a Q_online(s', a)
       - Target network evaluates that action: Q_target(s', a*)
       - TD target: r + γ × Q_target(s', argmax_a Q_online(s', a))

       Benefit: Reduces Q-value overestimation, more stable training

   4.2.6 FILE LOCATIONS

       Location: hems_core/agents/dqn/

       │   - select_action(state, explore)

4.3 SAC AGENT DETAILS

   Algorithm: Soft Actor-Critic (Maximum Entropy Reinforcement Learning)

   4.3.1 ARCHITECTURE

       Actor Network:
       Input: State (9,)
         │
         ▼
       - Linear(9, 256) + ReLU
       - Linear(256, 256) + ReLU
         │
         ├──────────────┬──────────────┐
         ▼              ▼
       μ (mean)    log_std (variance)
       Linear→      Clamp[-20, 2]→Exp
         │                 │
         └────────┬────────┘
                  ▼
           Normal Distribution N(μ, σ)
           Sample: a = tanh(z), z ~ N(μ, σ)

       Critic Networks (x2):
       Input: State (9,) + Action (2,) concatenated
         │
         ▼
       - Linear(11, 256) + ReLU
       - Linear(256, 256) + ReLU
       - Linear(256, 1)
         │
         ▼
       Q-value estimate

       Why Two Critic Networks?
       - Reduces overestimation bias
       - Takes minimum: Q_target = min(Q1_target, Q2_target)
       - More stable learning

   4.3.2 HYPERPARAMETERS

       Learning Rates (Adam optimizer):
       - Actor learning rate (α_actor): 3e-4
       - Critic learning rate (α_critic): 3e-4
       - Entropy coefficient learning rate (α_entropy): 3e-4

       Discount Factor (γ): 0.99

       Network Size (HIDDEN_DIM): 256

       Soft Update Coefficient (τ): 0.005
       - Update rule: θ_target ← τ·θ + (1-τ)·θ_target
       - Applied to both Q1 and Q2 targets

       Action Log-Std Bounds:
       - LOG_STD_MIN: -20 (very low variance)
       - LOG_STD_MAX: 2 (reasonable variance)
       - Purpose: Prevents numerical instability

       Replay Buffer:
       - Capacity: 10,000 transitions
       - Batch size: 256
       - Sampling: Uniform random

       Entropy Coefficient (α):
       - Automatic tuning enabled
       - Target entropy: -action_dim = -2
       - Objective: Maintain exploration level

   4.3.3 MAXIMUM ENTROPY OBJECTIVE

       Standard RL Objective:
       J(π) = E_τ[Σ γ^t r(s_t, a_t)]

       SAC Objective (with entropy regularization):
       J(π) = E_τ[Σ γ^t (r(s_t, a_t) + α H(π(·|s_t)))]

       Where H(π) = -E_a[log π(a|s)] is policy entropy

       Benefits:
       - Encourages exploration (high entropy)
       - Prevents premature convergence to deterministic policy
       - Discovers multiple optimal solutions

   4.3.4 ACTOR UPDATE

       Actor Loss:
       L_actor = E_s[-log π(a|s) × (Q(s,a) - α log π(a|s))]
                                     └─ entropy term ─┘

       Interpretation:
       - Maximize expected Q-value
       - Maximize policy entropy (α controls tradeoff)

   4.3.5 CRITIC UPDATE

       For Q1 and Q2 networks:

       Q-target:
       Q_target(s, a) = r + γ(1 - done) × min(Q1_target(s', a'), Q2_target(s', a'))
       
       where a' ~ π(·|s')

       Critic Loss:
       L_Q = E[(Q(s,a) - Q_target)^2]

       Both Q1 and Q2 networks trained identically

   4.3.6 ENTROPY COEFFICIENT UPDATE (Automatic)

       Objective: Maintain H(π) near target entropy

       α Update:
       L_α = -α × (log π(a|s) + target_entropy)

       Schedule:
       - Updates every training step
       - Adaptive to policy entropy changes
       - Prevents α explosion/saturation

   4.3.7 TRAINING ALGORITHM

       For each episode:
       1. Reset environment, get s_0
       2. For each step t = 0 to 95:
          a) Sample action: a_t ~ π(·|s_t)
          b) Execute: (s', r, done, info) = env.step(a_t)
          c) Store transition: buffer.push(s, a, r, s', done)
          d) Every update_freq steps:
             - Sample batch from buffer (uniform)
             - Compute Q-targets: r + γ × min(Q1', Q2')
             - Update Q1, Q2: minimize (Q - Q_target)^2
             - Sample new actions: a' ~ π(·|s)
             - Update actor: maximize Q(s, a') + α H(π)
             - Update α: maintain entropy target
             - Soft-update target networks

   4.3.8 KEY DIFFERENCES FROM DQN

       ┌────────────────┬──────────────┬──────────────────┐
       │ Aspect         │ DQN          │ SAC              │
       ├────────────────┼──────────────┼──────────────────┤
       │ Policy Type    │ Deterministic│ Stochastic       │
       │ Exploration    │ ε-greedy     │ Entropy reg.     │
       │ Action Space   │ Discrete     │ Continuous       │
       │ Networks       │ 1 Q-network  │ 1 Actor + 2 Q    │
       │ Off-policy     │ Yes          │ Yes              │
       │ Stability      │ Moderate     │ High (2 critics) │
       │ Complexity     │ Low          │ Medium           │
       │ Convergence    │ Variable     │ Stable           │
       └────────────────┴──────────────┴──────────────────┘

5.1 DQN DUELING NETWORK

   Class: hems_core/agents/dqn/networks.py :: DuelingDQN

   Architecture:
   ┌─────────────────────────────────────────────────────────┐
   │                    Input State (9)                       │
   └────────────────────┬────────────────────────────────────┘
                        ▼
   ┌──────────────────────────────────────────────────────────┐
   │                   Shared Trunk                            │
   │  Linear(9→256) + LayerNorm + LeakyReLU(0.1)             │
   │  Linear(256→256) + LayerNorm + LeakyReLU(0.1)           │
   └────────┬──────────────────────────┬──────────────────────┘
            ▼                          ▼
   ┌──────────────────────┐  ┌──────────────────────┐
   │   Value Stream V(s)  │  │ Advantage A(s,a)     │
   │ Linear(256→128)      │  │ Linear(256→128)      │
   │ + LayerNorm          │  │ + LayerNorm          │
   │ + LeakyReLU          │  │ + LeakyReLU          │
   │ Linear(128→1)        │  │ Linear(128→49)       │
   └──────────┬───────────┘  └──────────┬───────────┘
              │                         │
              │  Q(s,a) = V(s) + A(s,a) - mean(A(s,a))
              │                         │
              ▼─────────────────────────▼
   ┌─────────────────────────────────────┐
   │    Q-values for 49 discrete actions │
   │         Output shape: (49,)         │
   └─────────────────────────────────────┘

   Weight Initialization:
   - All Linear layers: Orthogonal initialization (gain=1.0)
   - Biases: Zero initialization

   Forward Pass:
   ```
   def forward(state):
       features = trunk(state)           # (B, 256)
       value = value_stream(features)    # (B, 1)
       advantage = adv_stream(features)  # (B, 49)
       q = value + advantage - advantage.mean(dim=1, keepdim=True)
       return q                          # (B, 49)
   ```

   Parameters:
   - CONFIG.STATE_DIM = 9
   - CONFIG.N_ACTIONS = 49
   - CONFIG.HIDDEN_SIZES = [256, 256]
   - CONFIG.VALUE_HIDDEN = 128
   - CONFIG.ADVANTAGE_HIDDEN = 128
   - Total parameters: ~200K

5.2 SAC ACTOR NETWORK

   Class: hems_core/agents/sac/networks.py :: Actor

   Architecture:
   ┌─────────────────────────────────────────────┐
   │         Input State (9)                      │
   └────────────────────┬────────────────────────┘
                        ▼
   ┌──────────────────────────────────────────────┐
   │    Linear(9→256) + ReLU                      │
   │    Linear(256→256) + ReLU                    │
   └────────┬────────────────────────────────────┘
            ▼
   ┌────────────────────┬───────────────────────┐
   │  μ head (mean)     │  log_σ head (log_std) │
   │ Linear(256→2)      │ Linear(256→2)         │
   │                    │ Clamp[-20, 2]         │
   │                    │ Exp → σ               │
   └────────┬───────────┴───────────┬───────────┘
            │                       │
            ▼                       ▼
   ┌─────────────────────────────────────────┐
   │  Sample: z ~ N(μ, σ)                    │
   │  Action: a = tanh(z) ∈ [-1, 1]         │
   │  Log-prob: log π(a|s)                  │
   └─────────────────────────────────────────┘

   Key Methods:
   
   forward(state):
   - Returns (μ, σ) of action distribution
   
   sample(state):
   - Returns (action, log_probability)
   - Reparameterization trick for backprop
   - Tanh transformation for bounded output
   - Log-prob corrected for tanh jacobian:
     log π(a|s) = log p(z) - log(1 - tanh²(z))

   Parameters:
   - Hidden dimension: 256
   - Output dimension: 2 (continuous action)
   - Total parameters: ~130K

5.3 SAC CRITIC NETWORK

   Class: hems_core/agents/sac/networks.py :: Critic

   Architecture:
   ┌────────────────────────────────────┐
   │  State (9) ⊕ Action (2)            │ (concatenation)
   │  Input dimension: 11               │
   └────────────────┬───────────────────┘
                    ▼

   │   Linear(256→256) + ReLU             │

6.1 MAIN TRAINING SCRIPT

   Location: main.py

   Main Function: train_sac()

   Parameters:
   - num_episodes: Number of training episodes (default: 100)
   - batch_size: Training batch size (default: 256)
   - update_freq: Update every N steps (default: 1)
   - model_save_freq: Save checkpoint every N episodes (default: 20)

   Execution Flow:
   1. Initialize EnergyEnv()
   2. Initialize Agent (SACAgent or DQNAgent)

   4. Save configuration to JSON
   5. For each episode:
      - Reset environment

        a) Agent selects action (exploration mode)
        b) Environment executes action
        c) Collect (state, action, reward, next_state, done)
        d) Store in replay buffer
        e) Agent updates networks (every update_freq)
        f) Log step data
      - Log episode summary
      - Save model checkpoint (every model_save_freq)
   6. Save final model and training data

   Key Parameters to Adjust:

================================================================================
11. ALGORITHM SELECTION GUIDE
================================================================================

11.1 WHEN TO USE DQN

   Advantages:
   - ✓ Stable training with experience replay
   - ✓ Prioritized replay focuses on hard experiences
   - ✓ Well-understood, extensive literature
   - ✓ Good for discrete or discretizable action spaces
   - ✓ Lower sample complexity with PER

   Disadvantages:
   - ✗ Discrete action space only
   - ✗ Epsilon-greedy exploration less elegant
   - ✗ Off-policy critic can be unstable
   - ✗ Hyperparameter sensitive

   Best for:
   - Discrete action control
   - Learning from limited data
   - Deterministic environments
   - When stability is paramount

11.2 WHEN TO USE SAC

   Advantages:
   - ✓ Continuous action space naturally supported
   - ✓ Entropy regularization encourages exploration
   - ✓ Stable learning (two critics reduce overestimation)
   - ✓ Automatic entropy tuning
   - ✓ Generally requires less hyperparameter tuning

   Disadvantages:
   - ✗ More complex implementation (3 networks)
   - ✗ Higher computational cost
   - ✗ Entropy tuning adds complexity
   - ✗ Larger replay buffer required

   Best for:
   - Continuous control tasks
   - Exploration-exploitation balance needed
   - When smooth, stochastic policies desired
   - Complex, high-dimensional action spaces

11.3 WHEN TO USE PPO

   Advantages:
   - ✓ On-policy, more direct policy optimization
   - ✓ Trust region prevents large policy changes
   - ✓ Simpler than actor-critic methods
   - ✓ Good sample efficiency with parallel environments

   Disadvantages:
   - ✗ On-policy: less data efficient for offline learning
   - ✗ Requires large batch sizes
   - ✗ Sensitive to hyperparameters
   - ✗ Not ideal for small replay buffers

   Best for:
   - Multiple parallel environments
   - Real-time interaction requirements
   - When policy divergence must be controlled
   - High-dimensional observation spaces

12. IMPLEMENTATION DETAILS & BEST PRACTICES
================================================================================

12.1 DEVICE MANAGEMENT

   Automatic Device Selection (in order):
   1. Check if CUDA available → use "cuda"
   2. Check if MPS available (Apple Silicon) → use "mps"
   3. Fallback → use "cpu"

   Code:
   ```python
   if torch.cuda.is_available():
       device = "cuda"
   elif getattr(torch.backends, "mps", None) and torch.backends.mps.is_available():
       device = "mps"
   else:
       device = "cpu"
   ```

   Verification:
   ```python
   print(f"Using device: {device}")
   # Expected output: "Using device: cuda" or "cpu" or "mps"
   ```

12.2 REPRODUCIBILITY

   Setting Random Seeds:
   ```python
   import random, numpy as np, torch

   seed = 42
   random.seed(seed)
   np.random.seed(seed)
   torch.manual_seed(seed)
   ```

   Benefits:
   - Reproducible training runs
   - Consistent results for debugging
   - Fair comparison between algorithms

12.3 GRADIENT STABILITY

   Gradient Clipping (DQN):
   - Clips L2 norm to max_norm
   - Prevents exploding gradients
   - Typical value: 10.0

   Code:
   ```python
   nn.utils.clip_grad_norm_(network.parameters(), max_norm=10.0)
   ```

   Layer Normalization:
   - Applied in DQN trunk
   - Reduces internal covariate shift
   - Improves training stability

12.4 EXPLORATION STRATEGIES

   DQN ε-greedy:
   - Deterministic exploration
   - Linear decay schedule
   - Good for discrete actions

   SAC Entropy:
   - Stochastic exploration
   - Automatic tuning
   - Encourages high-entropy policies

   Comparison:
   ┌──────────────────┬──────────┬──────────────┐
   │ Aspect           │ ε-greedy │ Entropy Reg. │
   ├──────────────────┼──────────┼──────────────┤
   │ Simplicity       │ High     │ Medium       │
   │ Smoothness       │ Low      │ High         │
   │ Sample Efficiency│ Good     │ Very Good    │
   │ Convergence      │ Variable │ Stable       │
   └──────────────────┴──────────┴──────────────┘

12.5 NETWORK INITIALIZATION

   Orthogonal Initialization (DQN):
   ```python
   nn.init.orthogonal_(layer.weight, gain=1.0)
   nn.init.zeros_(layer.bias)
   ```

   Benefits:
   - Preserves gradient flow through deep networks
   - Prevents vanishing/exploding gradients
   - Improves convergence speed

12.6 SOFT TARGET UPDATES

   Polyak Averaging Formula:
   θ_target ← τ·θ_online + (1-τ)·θ_target

   Benefits:
   - Smooth target network updates
   - Prevents sudden policy changes
   - Improves stability

   Typical τ values:
   - DQN: 0.005 (soft update)
   - SAC: 0.005 (soft update)
   - Hard update: τ=1.0 (DQN typical hard update)

13. PERFORMANCE OPTIMIZATION TIPS
================================================================================

13.1 TRAINING SPEED IMPROVEMENTS

   1. Use GPU (NVIDIA CUDA):
      - ~10x faster than CPU for neural networks
      - Transfer batch to GPU before computation

   2. Batch Processing:
      - Larger batches (256-512) are more efficient
      - Trades off against memory usage

   3. Data Caching:
      - Real data loaded once, cached in memory
      - Subsequent accesses are O(1)

   4. Reduce Logging Frequency:
      - Log every N episodes instead of each
      - Saves I/O overhead

   5. Asynchronous Environments:
      - Run multiple environment copies in parallel
      - Collect experience faster

13.2 MEMORY OPTIMIZATION

   1. Replay Buffer Management:
      - DQN: Use circular buffer (deque with maxlen)
      - Automatically drops old samples
      - Fixed memory footprint

   2. Checkpoint Storage:
      - Save only last N checkpoints
      - Delete old ones to save disk space

   3. Gradient Computation:
      - Use torch.no_grad() for inference
      - Prevents unnecessary gradient accumulation

   Code:
   ```python
   with torch.no_grad():
       q_values = network(state)  # No grad tracking
   ```

13.3 NUMERICAL STABILITY

   1. Log-Sum-Exp Trick (SAC entropy):
      - Compute in log space to prevent overflow
      - PyTorch distributions handle this

   2. Layer Normalization (DQN):
      - Normalizes activations per sample
      - Improves numerical stability

   3. Gradient Clipping:
      - Prevents NaN/Inf propagation
      - Essential for deep networks


================================================================================
14. TROUBLESHOOTING COMMON ISSUES
================================================================================

14.1 TRAINING NOT CONVERGING

   Symptoms:
   - Reward remains constant or deteriorates
   - Loss increasing over time
   - Agent not learning behavior

   Solutions:
   1. Check learning rate:
      - Too high: try 1e-4
      - Too low: try 1e-3
   
   2. Verify data loading:
      - Check data files exist
      - Print sample states to verify normalization
   
   3. Inspect rewards:
      - Are rewards being calculated correctly?
      - Check cost calculation
   
   4. Network architecture:
      - Try larger/smaller networks
      - Add/remove layers

14.2 OUT OF MEMORY ERRORS

   Symptoms:
   - "CUDA out of memory" or similar
   - Training crashes after N episodes

   Solutions:
   1. Reduce batch size: 256 → 128 → 64
   2. Reduce buffer capacity: 100K → 50K
   3. Use CPU instead of GPU (slower but works)
   4. Run fewer episodes before checkpoint

14.3 UNSTABLE TRAINING (HIGH VARIANCE)

   Symptoms:
   - Reward fluctuates wildly
   - Loss spikes randomly
   - Performance inconsistent

   Solutions:
   1. Increase batch size: 128 → 256 → 512
   2. Reduce learning rate: 3e-4 → 1e-4
   3. Increase τ (softer updates): 0.01
   4. Use layer normalization (already in DQN)

14.4 SLOW TRAINING

   Symptoms:
   - Takes too long to train
   - Single episode slow

   Solutions:
   1. Use GPU: 10x speedup possible
   2. Reduce data loading (caching enabled)
   3. Use smaller network
   4. Skip visualization during training
   5. Run fewer checkpoints (SAVE_INTERVAL)
